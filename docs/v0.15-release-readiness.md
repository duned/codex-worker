## Installation and execution boundary

A clean Ubuntu 24.04 x64 node can install the self-contained Worker and register without Git, GitHub CLI, Codex CLI or their authentication. Registration persists the identity, durable credential and Server URL. Installer success and a systemd `Type=exec` start request do not establish execution readiness.

The current host still requires global authenticated Codex preflight, including with an empty managed project snapshot. Missing Codex stops startup with exit code 2; the packaged unit prevents restart loops. The registered node can subsequently appear offline and its local API can be unavailable. Neither condition invalidates registration. Diagnose the service-account executable/environment and journal rather than deleting identity or consuming more bootstrap tokens. Project-specific Git/GitHub readiness failures mark projects unavailable; if none of the configured projects can start, startup stops. A healthy project can initialize independently, but it cannot bypass global Codex preflight.

v0.16 owns the general capability inventory, an online unprovisioned lifecycle, Server-driven Git/gh/Codex installation, secure GitHub/SSH and Codex authentication, and provisioning UI. Existing limited policy-controlled provisioning handlers are retained for compatibility; they are not an installer prerequisite or a clean-node workaround. Do not copy interactive-user credentials, add automatic tool installation, or manually log in solely to pass the v0.15 clean-node checkpoint. Execution regression evidence must come from an already-provisioned environment.

## Findings addressed by this checkpoint

1. The quick-start and original E2E plan implied an empty unprovisioned Worker would stay online. They now state the actual Codex preflight boundary and separate clean-node registration from provisioned execution scenarios. Historical provisioning exercises are explicitly optional regression coverage, not v0.15 acceptance workarounds.
2. The README described project startup errors as globally fatal despite the isolated host startup path. It now distinguishes project unavailability from global failure; added tests verify the phases compose with healthy-project initialization.
3. The README used a stale packaged Server backup executable path and called the post-bootstrap credential a registration token. It now uses `current/CodexServer`, distinguishes retained database paths, and identifies the durable per-Worker credential.
4. Release solution configuration had a truncated test-project GUID. A Release build reported MSB4121 and omitted the test configuration. Both mappings now use the declared project GUID, so Release validation includes tests. This focused build-configuration correction introduces no lifecycle feature.

No additional runtime blocker was identified in this review. This is limited to the inspected code and available local tests; it does not establish clean-host or external-service behavior by itself. If deployment verification reveals another hardening regression, record a focused 15.x follow-up and keep release closure pending. Record provisioning gaps under v0.16 instead.

## Validation and release closure

The local release, installer, Worker installer lifecycle, and uninstaller lifecycle shell suites passed. They use temporary relocated paths and service/process stubs, exercising real archive/checksum and filesystem decisions without external-service access. They do not prove real systemd startup or network authentication.

The normal repository restore/build/test sequence was attempted. Single-node restore failed with NU1301 because sandbox network access to `api.nuget.org:443` was denied, so compilation and xUnit execution could not complete. The initial Release check exposed the solution GUID defect above; after correction, the configuration no longer reports MSB4121. Worker-configured validation remains the authoritative gate. Do not infer that gate passed from this checkpoint.

Before release closure, retain evidence from the supported version-pinned [packaged flow](linux-installation.md) for Server startup/token database selection, Worker registration with stable identity, accurate missing-tool diagnosis and no restart loop, normal uninstall/reinstall identity retention, and purge/reinstall convergence. Use the amended [E2E plan](e2e-test-plan-v1.md) for the already-provisioned execution, concurrency, integration and reporting campaign. Actual Linux x64 publishing, real VM lifecycle, live GitHub/Codex/Telegram and release publication require an appropriate environment; no live campaign or publication was performed here.

The intended transition remains: resolve true 15.x blockers and pass validation → release v0.15.0 → v0.16 Provisioning. This checkpoint does not bump the source version or publish a release.
