# Codex Server capability and administration audit (18.1)

Baseline: checkout `07e4e05`, reviewed for Issue #141. This is a source/test/documentation audit, not a live deployment certification or a product-version change. No missing feature is implemented and no follow-up GitHub Issues are created here.

**Finding:** the Server has a persistent managed execution control plane and substantial node provisioning. It lacks a coherent local administration interface, central enable/disable controls, and Server-owned GitHub Issue administration. Existing Worker operations must not be mistaken for Server capabilities.

## Method and evidence key

Reviewed route handlers, CLI dispatch, dashboard callers, SQLite stores/migrations, shared provisioning handlers, representative Worker execution paths, automated test cases, and the operator documentation. **Implemented** means the scoped behavior exists; **Partial** means only part of the named capability exists; **Missing** means no supporting Server contract/service/surface was found; **Legacy / duplicated** identifies overlapping paths or supported older contracts. Tests below are evidence of checked-in coverage, not a claim that the authoritative Worker validation ran. Missing capabilities have no direct positive regression coverage; adjacent tests establish the existing boundary.

## Architectural and exposure conclusions

1. **Preserve ownership:** registry/projects/leases belong to Server; execution, Git/GitHub lifecycle and physical workspace recovery belong to Worker. A new Server CLI should adapt the existing Server services/contracts, not open an alternate registry or execute Worker Git mutations.
2. **Resolve verified overlap:** management state transitions and normal assignment/report flows have different checks; provisioning plans and typed commands have different replay semantics. These are behavior differences, not merely duplicate endpoint names.
3. **Keep representations explicit:** scheduling `WorkerCapability`/`ProjectRequirement` and typed node inventory coexist for different purposes. Legacy string converters, contract v1/v2 support, shared registration-token fallback and `DatabasePath` override are supported compatibility boundaries. They should be documented/reviewed, not removed incidentally.
4. **Expose facts consistently:** HTTP supports plan creation, enqueue/state transitions and command cancellation/reconciliation that the dashboard cannot administer. The Server CLI now exposes local status, projects, credentials and typed provisioning alongside token/backup operations. Worker diagnostics ignore typed-command errors; node readiness is not project readiness. Operator-facing summaries need to explain these distinctions without inventing another lifecycle.
5. **Documentation limitations:** README and node docs describe the current layered behavior, including manual GitHub/SSH steps. The backup manifest/validator and README's initial plan-installer limitations should be read in their specific protocol scope; they do not describe all newer typed commands. No end-to-end clean Server administration campaign establishes parity across CLI/API/UI today.
