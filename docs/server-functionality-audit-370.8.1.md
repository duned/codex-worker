## Findings and corrections

**F1 — Fixed: return the project revision actually written.** Definition and lifecycle updates used a revision-conditional `UPDATE`, followed by `GetProjectAsync` on another connection. Between those operations another accepted edit could advance the row, so the first caller could receive another editor's definition/revision. Both updates now use `UPDATE ... RETURNING` and the existing `ToProject` mapper. This removes the successful-path second query/connection without removing the authoritative revision predicate, uniqueness enforcement, field validation or conflict/not-found handling. The unsuccessful path still reads current state to distinguish those outcomes. Definition updates now reject nonpositive revisions at the store boundary, matching lifecycle/delete and HTTP validation; local administration also uses this store.

Added `CentralProjectMutationReturnsItsOwnRevisionWhenTheStoredRowAdvances` for both operations. A local SQLite AFTER trigger deterministically advances the stored row to revision 3 after the statement captures revision 2, avoiding a timing-dependent concurrent-writer test. Assertions distinguish returned/stored revisions, description and enabled state. Added `CentralProjectMutationsRejectNonpositiveRevisionsWithoutChangingState` for zero/negative revisions, existing/missing IDs, and all three mutation contracts. Existing CRUD, uniqueness, concurrent revision conflict, lifecycle and validation-command tests remain applicable.

**F2 — Fixed: backup must not restore MCP authorization.** `McpOAuthStore` persists consent grants and hashed code/access/refresh credentials, bound to the management authority and issuer. `ServerBackup.ScrubSecretsAsync` scrubbed Worker tokens and credentials but omitted these later-added tables. Restoring an earlier archive with unchanged management authority/origin could restore a subsequently revoked MCP grant/token. Hashing prevents reading bearer tokens from the archive but does not prevent a caller holding the original token from using restored authorization.

Export now deletes both optional OAuth tables in its existing copy/scrub transaction; the live database is unchanged. Archive validation rejects either nonempty table, including an old unsanitized archive, before offline replacement. Older archives without these tables still work. Fresh administrator consent is required after restore; operator/security docs now say so. `BackupRemovesOAuthAuthorityAndRejectsArchivesThatRetainIt` creates real code/access/refresh grants, verifies restored denial with unchanged authority, verifies the source stays authorized, and injects unsanitized snapshots to check each table independently and preservation of the existing restore target on refusal. The existing backup round trip covers archives with no OAuth tables.

No scheduling, lease, recovery or authorization guard was removed. Checks repeated across the API, store, Worker and external provider generally protect different trust boundaries or different moments in time; apparent duplication alone is insufficient evidence for deletion.

## End-to-end workflow traces

1. **Project definition to managed configuration.** Authenticated HTTP or local administration validates the definition; the registry normalizes and stores a revisioned central project. Lifecycle and definition changes share the revision. The authenticated Worker configuration route obtains current projects/settings and produces a managed snapshot through the existing shared/Worker contract. Worker snapshot validation/application remains atomic and machine-specific paths remain Worker-owned. A configured slot change blocks new admission until the Worker reports the new capacity. Disabling a project stops new enqueue/admission while preserving active leases; deletion rejects queued/assigned/running references. A cached snapshot grants no outage scheduling authority.
2. **Discovery to lease.** Manual enqueue and automatic discovery call `ServerGitHubAdministrationService.EnqueueIssueCoreAsync`, start a fresh read scope, load the current enabled project, canonicalize repository/Issue identity, check provider eligibility, and enqueue under current project revision/incarnation. Automatic discovery adds bounded pages/deadline and terminal-history rules, not a second queue. Worker assignment polling authenticates the exact Worker, opens a fresh GitHub read scope and enters transactional registry admission. The database write gate serializes policy/capacity checks and reservation; candidate engine/repository requirements, advertised capacity and fleet project limit all apply. An assignment carries current project data, assignment ID and lease generation. Final eligibility failure rejects that reservation through the existing lifecycle rather than authorizing execution from a discovery cache.
3. **Execution to terminal acknowledgement or expiry.** The Worker owns claim/worktree/implementation/validation/integration/reporting; Server APIs accept bounded stage/results only for the authenticated Worker and exact assignment/current unexpired generation. Stage reports cannot regress lifecycle; first stage timestamps survive repeats. Terminal result and lease release share a transaction. A matching repeat terminal report returns the committed result after a lost acknowledgement. Unknown identity is 404 and stale ownership/lifecycle is 409. Renewal and expiry keep generation fencing. Expiry creates a linked fresh-workspace attempt only in safe pre-integration stages; integration/reporting uncertainty reserves the Issue and capacity until explicit proof/recovery. Node-bound recovery does not authorize a different Worker or base.
4. **Uncertain execution and historical completion.** Operator reconciliation first requires the expired uncertain state and evidence, and serializes retry reservation against enqueue. Verified non-integration produces a linked attempt; integrated state does not automatically rerun implementation. Completion quarantine remains a Worker-owned preserved history outcome. Maintenance inventories can restore only absent exact assignment/local identity; they do not grant a lease. Completion preview/apply requires drain, exact original IDs/generation, eligible terminal state, no conflicting Issue ownership and a matching proof. `ReportExecutionCoreAsync` rechecks those guarantees transactionally for the narrow reconciliation operation. Repeated checks here cover dispatch-to-mutation races and must remain.
5. **Provisioning and credential delivery.** Management chooses a validated catalog action, creates an audited command for an existing node, and receives metadata. A Worker with its own API token claims only its node's command; the Server-local hosted executor claims `server`. Claiming and state transitions serialize in SQLite; running commands are not replayed. The shared executor selects product-owned executable/argument lists and applies node-local permission/elevation, cancellation and deadline. Reports validate ownership and bounded structured results; active login challenges expire and are removed on terminal outcomes. Separately, management assigns an encrypted provider credential, while the enrolled Worker establishes its own delivery verifier through a bounded confirmation operation. Delivery requires the independent exact-Worker token plus Ready/assigned credential; management/API auth cannot substitute. Node private keys and CLI caches stay local.
6. **Maintenance/update and reconnect.** Management requests a scoped durable operation; a pending operation may be cancelled, but dispatched uncertainty retains its slot. Worker maintenance reauthorizes inside its local drain/repository gate before mutation. Update/restart uses the assignment admission write gate, captures prior drain policy and capabilities, waits for no assignments/leases/executions and fresh heartbeat, then dispatches once. Installer verification, expected version, synchronization, readiness and (for restart) replacement instance all precede success/drain restoration. Explicit retry creates a new operation identity; failed restart drain release retains failure and requires idle/fresh evidence. Journal reads and Telegram tests are separate bounded Worker-mediated protocols, not free-form remote shell execution.
7. **Browser/MCP and backup lifecycle.** Browser session creation requires exact origin/host plus management bearer; subsequent mutations require CSRF/origin and expiry/rotation checks. SSE joins request, host shutdown and session cancellation. The dashboard shares generation-scoped reads/live owner and preserves uncertainty after unconfirmed writes. MCP adds per-tool scopes, PKCE/client/resource/issuer-bound OAuth and replay revocation; it does not confer Worker/delivery authority. Backup copies live SQLite, scrubs authorization on the copy, validates schema/integrity/sanitization, then publishes an archive. Offline restore obtains exclusive access, validates the extracted database before replacing state and requires reprovisioning/reconsent. It does not restore deployment secrets or authorize uncertain execution replay.

## Concrete follow-ups

These are separate design/validation tasks, not assumed safe deletions or confirmed bounded defects left unfixed.

- **F3 — Clock consistency.** `NodeProvisioning.Describe`, `WorkerJournalRequests` and `MaintenanceAuthorityReasonAsync` read `DateTimeOffset.UtcNow`, while registry/command/session stores have injectable clocks. Follow-up: thread an existing clock seam through these projections/authorization deadlines and add exact-boundary fake-time tests, checking freshness and drain/lease behavior before changing comparisons. Do not combine freshness, execution readiness and lease validity into one cached flag.
- **F4 — Persisted command protocols and restore policy.** Legacy provisioning plans, typed provisioning, execution maintenance, Worker updates and Telegram tests have superficially similar dispatch but different replay, uncertainty, deadline and recovery semantics. Follow-up: inventory supported client versions and persisted states, specify migration/restore behavior for pending versus running commands (including Server-local pending commands), and add restart/mixed-version fixtures before considering retirement or shared transition logic. At-most-once behavior alone is not an interchangeable store contract.
- **F5 — Resource retention/paging.** Journal requests already prune expired entries on read and cap the dictionary at 64; retain those bounds. OAuth used-refresh verifiers persist for replay detection during a grant's lifetime; Worker/project collection APIs load full lists while execution queries are paged. Follow-up: measure realistic fleet/churn and token-refresh history, specify retention and stable pagination, then test bounded memory/database growth and replay detection before introducing pruning. No new retention store or arbitrary limits were added in this audit.
- **F6 — Service size and deployment acceptance.** `RegistryPersistence.cs` combines multiple cohesive flows but already has partials and a shared transaction boundary; `ServerAdministration.cs` combines CLI dispatch/adapters. Follow-up: extract by existing responsibility only when a concrete change needs it, preserving transaction/exception/CLI contracts. Separately run the documented [managed campaign](managed-worker-e2e.md), HTTPS proxy/logging checks in [secret protection](secret-protection.md), and rendered-screen comparison against approved references when a dashboard change is proposed. Local source review cannot certify deployed TLS, sudo, vendor login, proxy logging or visual fidelity.
