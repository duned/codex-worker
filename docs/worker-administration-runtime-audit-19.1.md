# Worker administration and runtime audit (19.1)

Source audit for Issue #177, after Worker 17.x and Server 18.x. This is an implementation and checked-in coverage review, not a live-node acceptance result or a product-version change. The findings below guide bounded 19.x child tasks; they do not authorize remote process control or a new scheduling architecture.

**Finding:** the Worker has reusable local administration services, bounded provisioning, durable enrollment and a substantial execution/recovery pipeline. Its administration views do not yet consistently explain the relationship between installed tools, node authentication, repository authorization and execution readiness. Preserve the existing ownership and execution boundaries while improving these views and closing the specific validation gaps below.

## Evidence and comparison baseline

Reviewed CLI dispatch, application services, configuration, registration/heartbeat/assignment, both provisioning paths, shared credentials and tool handlers, startup/readiness, execution preparation, history/recovery, and representative tests. **Implemented** means code exists within the stated scope; **Partial** identifies an incomplete surface; **Gap** identifies a concrete missing behavior or validation boundary. Test references describe checked-in coverage, not tests run for this audit.

The [18.1 Server audit](server-control-plane-audit-18.1.md) is historical: several of its missing capabilities were implemented by 18.x. Compare with current [Server administration](../src/CodexServer/ServerAdministration.cs), [Worker administration](../src/CodexServer/WorkerAdministrationCommand.cs), [credential administration](../src/CodexServer/CredentialAdministration.cs), [provisioning administration](../src/CodexServer/ProvisioningCommandAdministration.cs), and the [18.10 acceptance report](server-local-administration-18.10.md). Current Server conventions include service-backed CLI/API operations, bounded structured diagnostics, versioned output, optimistic project revisions, explicit queue reconciliation, and distinct scheduling policy, API authentication and credential-delivery authority.

The Worker should adopt those conventions where applicable. It must not acquire Server registry ownership, central credential storage, queue administration or an alternate assignment path. The [17.7 CLI campaign](worker-administration-cli-validation-17.7.md) establishes earlier isolated CLI evidence; it skipped successful host mutation and authentication and does not certify the findings here.

## Provisioning providers and tool requirements

Installation is a machine fact. Authentication is a separate observation. Repository authorization, service-account environment and successful execution preflight establish additional readiness. Neither a successful installer nor `auth status` alone authorizes an execution.

| Tool / provider | Authentication and configuration required | Remaining gap / acceptance boundary |
| --- | --- | --- |
| Git: shared typed apt provider (`git` plus `openssh-client`); legacy apt plan also maps Git | Git has no tool-level login. Shared inventory checks `user.name` and `user.email` in the probe context. Project startup verifies the checkout and actual remote read plus dry-run write; HTTPS helper or node-local SSH is required according to the remote. | Global identity probes do not prove repository-local identity or remote authorization. Node SSH verification is read access, not push/Issue permission. Report those scopes separately; do not make a missing global identity invalidate a valid repository-local identity without a defined contract. |
| GitHub CLI: shared apt provider for `gh` | `gh auth status --hostname github.com` in the effective trusted context; typed preparation/device login/logout use product-owned node-local state. Legacy credential plans accept assigned GitHub tokens through the shared token handler. Project readiness checks Issue access/write permissions independently. | Login does not prove all repositories are writable. Typed tool commands do not themselves assign or deliver Server-held tokens. Keep credential delivery and node login distinct, and explain the available route to satisfy each requirement. |
| Codex CLI: shared Node/npm provider for `@openai/codex@latest` | Node/npm are provider prerequisites, not authentication. `CodexServiceEnvironment` selects the service executable and `CODEX_HOME`; guided login and login status observe local authentication. Worker preflight performs a bounded actual invocation and expects exactly `OK`. | Installed and logged in can still fail execution due to environment, network, temporary-directory permissions or service authorization. Preserve that additional gate and useful safe failure reason. Central credential delivery currently has no Codex token materialization handler; do not imply that assigning any credential enables Codex. |
| Node, Docker, PostgreSQL: legacy `DebianAptDependencyInstaller` mappings (`nodejs`, `docker.io`, `postgresql-client`) | Node execution needs no generic login. Docker CLI presence does not establish daemon/socket access or registry authorization. `psql` presence does not establish database service availability, connectivity or credentials. | No typed lifecycle catalog parity for these tools. Discovery emits PostgreSQL as `tool`, but the legacy installer maps `service/postgresql`; installation verification and Server requirement matching need an explicit consistent contract before offering that plan as usable. The installed package is a client, not a provisioned database service. |
| .NET: version probe only | No generic login for local SDK execution; feeds used by project validation may require project-specific credentials. | No provider in either inspected install path. Self-contained Worker installation does not install an SDK for task validation. Explain unsupported provisioning; add a fixed provider only if a child task explicitly requires it. |

Provider evidence: [ToolProvisioningProviders](../src/Shared/ToolProvisioningProviders.cs), [NodeCapabilities](../src/Shared/NodeCapabilities.cs), [NodeGitHubSetup](../src/Shared/NodeGitHubSetup.cs), [CodexDeviceLogin and service environment](../src/Shared/CodexDeviceLogin.cs), [DependencyInstallers](../src/CodexWorker/DependencyInstallers.cs), [GitRepository](../src/CodexWorker/GitRepository.cs), [GitHubClient](../src/CodexWorker/GitHubClient.cs), [CodexExecutor](../src/CodexWorker/CodexExecutor.cs). ## Shared infrastructure and duplication

1. **Two discovery models remain.** [WorkerCapabilityDiscovery](../src/CodexWorker/WorkerCapabilityDiscovery.cs) probes versions of seven tools, always advertises `integration/github-issues`, and caches them separately from shared `NodeCapabilityDiscovery`. The shared catalog covers three tools and their auth/config/health. An integration declaration describes implemented support, not successful authentication. Reuse shared probes for overlapping tools through an explicit projection while retaining broader runtime requirements; do not silently replace the scheduling wire model with the three-tool catalog.
2. **Two provisioning lifecycles remain.** [ProvisioningPlanExecutor](../src/CodexWorker/ProvisioningPlanExecutor.cs) handles legacy refresh, install/ensure and credential actions with Worker installers. Typed commands use [WorkerProvisioning](../src/CodexWorker/WorkerProvisioning.cs) and shared `NodeProvisioningCommandExecutor`, with update/uninstall, deadlines, redetection and command history. Git apt operations, version matching and policy classification overlap but have different contracts. Establish supported persisted/protocol compatibility before converging overlapping behavior; preserve the broader legacy requirements and action-specific denial semantics.
3. **Credential handling is already partly shared.** [GitHubAuthenticationProvisioner](../src/CodexWorker/AuthenticationProvisioning.cs) delegates token validation/stdin login to [GitHubTokenAuthentication](../src/Shared/GitHubTokenAuthentication.cs). Server storage/delivery uses [shared credential infrastructure](../src/Shared/CredentialProvisioning.cs). Keep Worker repository readiness and delivery authorization at their existing boundaries; do not duplicate a secret store locally. Worker auth provisioner catches retrieval/readiness failures into safe generic results; improve bounded diagnostic codes if required without exporting secret-bearing exception text.
4. **Policy/action presentation overlaps.** `WorkerProvisioning.Decide` and `WorkerProvisioningAdministrationService.ActionAvailability` reconstruct action keys, privileged/read-only groups and platform explanations. Share actual classification where needed, preserving Worker-local final permission. CLI strings such as `upgrade` map to protocol `Update`; advertised action names and policy keys must remain unambiguous.

Coverage to retain: [ToolProvisioningLifecycleTests](../tests/CodexWorker.Tests/ToolProvisioningLifecycleTests.cs), [ProvisioningCommandTests](../tests/CodexWorker.Tests/ProvisioningCommandTests.cs), [ProvisioningPlanExecutorTests](../tests/CodexWorker.Tests/ProvisioningPlanExecutorTests.cs), [WorkerProvisioningTests](../tests/CodexWorker.Tests/WorkerProvisioningTests.cs), [SharedCredentialServicesTests](../tests/CodexWorker.Tests/SharedCredentialServicesTests.cs), [AuthenticationReadinessTests](../tests/CodexWorker.Tests/AuthenticationReadinessTests.cs).

| Enrollment is independent of execution — **Implemented** | [WorkerRegistration](../src/CodexWorker/WorkerRegistration.cs) persists stable identity, generated API token and `.server` endpoint; bootstrap can recover an already-consumed token via authenticated registration. ## E2E campaign needed after the bounded changes

Extend the existing [E2E plan](e2e-test-plan-v1.md) in a separately scoped campaign. That document contains release-specific v0.15 and older provider limitations; retain historical results and reconcile source-vs-released-artifact expectations before using it as current provisioning acceptance. Issue series do not set a product version.

1. **Clean service account:** install the selected self-contained artifacts with Git, gh, Codex and task runtimes initially absent. Collect status, config validation and inventories; enroll an empty managed Worker. Confirm persistent identity and online/provisionable state with no execution assignment.
2. **Install/authentication separation:** under explicit local allowlists and elevation, install typed tools one at a time. Verify installation alone leaves authentication/configuration required. Exercise denied operations before allowed ones and record provider/platform limitations rather than manually hiding them.
3. **Effective service environment:** perform Git configuration, node GitHub preparation/login or assigned-token delivery, SSH public-key enrollment where needed, and Codex device login as the Worker account. Confirm executable/PATH, home and temporary-directory permissions; prove an operator's login does not substitute for service-account readiness. Never retain device codes, private keys, tokens or environment contents in evidence.
4. **Repository and execution gates:** configure a dedicated test checkout and central project with machine-local execution settings. Compare CLI, running Worker and Server views. Verify `gh` login with insufficient Issue permission and SSH read-only access both fail the appropriate project gate. Then run one normal execution through isolated worktree, authoritative project validation, lease-fenced integration and reporting.
5. **Regression and recovery:** revoke/logout authentication while safely idle, drain with active work, restart after interrupted provisioning/report delivery, and temporarily disconnect Server. Confirm no fresh managed work during outage, no command replay, retained identity/workspaces/history and explicit uncertain-state reconciliation. Exercise bounded recovery with verified ownership; preserve unrelated active work on safe task failure.

Use disposable approved nodes/repositories for mutations and record non-secret execution/command IDs, versions and concise diagnostics. Deterministic automated tests should precede this campaign; live GitHub/Codex success, TLS deployment and real-node lifecycle evidence require their own environment and authorization.

## Audit outcome and validation

This change adds the audit and a README entry only. No runtime, protocol, persistence, provider, credential, configuration or version changes are made: the identified corrections require focused contract choices and regression coverage in the bounded child tasks. Source/test consistency, Markdown link targets and diff whitespace were reviewed locally. No build, test suite or live E2E campaign was run for this documentation-only change; the Worker's separately configured checks remain the authoritative integration gate.
