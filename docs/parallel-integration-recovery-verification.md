# Parallel integration and recovery verification

## First-attempt integration

`GitWorktreeTests.FirstAttemptsIntegrateFromSameBaseInEitherOrder` exercises two original executions through `ExecutionRunner`, isolated worktrees, the shared repository gate, validation, rebase, conflict resolution and push to a temporary local bare remote. Both implementations start at the same commit before either may integrate. Explicit signals select either completion order without sleeps. The configured base is `integration`, rather than the fixture's default `main`.

The cases cover disjoint changes and overlapping changes with a resolver that retains both tasks' behavior. They assert different worktrees and branches, a common starting commit, post-rebase validation of the combined source, preservation of both changes, and matching local/remote base tips. Managed cases supply separate execution/assignment identities and authority checks. Standalone overlap uses the same Git and Issue-verification path without a Server lease.

A managed original execution no longer needs `RetryOf` to prove intent. Verification compares the live open Issue, lifecycle labels and parent with the current execution's captured title, body fingerprint and parent metadata. Explicit conflict recovery continues to verify the preserved source's original intent and lineage. Clean managed integration recovery retains its existing lease-authorized path and frozen execution profile; it requires additional live Issue proof if conflict editing becomes necessary. Managed ownership is checked before and after resolution, and both intent and ownership are checked again before integration mutations after resolution. The existing engine receives the current Issue and Git's configured base, replayed commit and conflicted index; its prompt requires preserving compatible base behavior. Validation remains authoritative; a model's success result alone never authorizes integration.

Conflict resolution uses `validation.maxFixAttempts` as its budget. Exhaustion, structured resolver failure and known Issue-verification refusals return an integration-conflict outcome. Partial edits and any in-progress rebase remain preserved, with recovery guidance and automatic retry disabled. Further conflicts in a multi-commit rebase also retain partial work. Review that workspace and original implementation branch before another recovery action. These contained outcomes do not require restarting the Worker. Unverified Git history changes, engine infrastructure errors, lease loss and uncertain push results retain the existing infrastructure/reconciliation semantics.

The new first-attempt cases also cover exhausted resolution budget, failed resolution, changed intent after resolution, lease loss, failed combined-source validation and a resolver that changes Git history. Existing tests cover push uncertainty, bounded post-rebase validation retry, cancellation, shutdown, recovery ownership and continued scheduling after safely contained failures.

## Session inheritance and incident evidence

The VM2 v0.34.10 incident reports a first attempt with no `RetryOf` and the diagnostic `Conflict resolution requires authoritative Issue verification`. Code inspection establishes a direct mismatch: managed executions were eligible to resolve conflicts, but verification unconditionally required prior execution history. This is independent of session inheritance. The reported lack of native blockers and skipped inheritance is consistent with intentional fresh-session selection; it does not establish incorrect worktree selection. The failed external #44 execution was neither inspected nor changed by this implementation.

History inspection isolates the regression from the earlier inheritance changes: `ab2aa56` (#493) added managed conflict recovery but retained a prior-execution requirement; `3220b61` (#491) then enabled the resolver for original managed integrations and broadened eligibility to every managed execution without changing that requirement. `620e14b` (#495) added explicit managed recovery Issue checks, and `f912fee` (#497) added parent-proof comparison. Those later recovery checks did not repair original-attempt verification. The earlier inheritance commits and explicit child-directory contract are described in the historical investigation; no branch/base-selection change is needed for this fix.

`BlockerCodexSessionTests.OnlyCompatibleAuthoritativeBlockersSupplyAThread` verifies eligible inheritance and intentional skips, including no native blockers. `InheritedThreadUsesChildPromptProfileAndExplicitWorktree` runs a stub CLI to verify actual resume arguments, explicit child CWD, current Issue prompt/profile, and observable fresh fallback when resume is unsupported or the thread is missing. `CodexThreadCoordinatorTests` verifies same-thread serialization, eligibility revalidation and concurrent fresh/different sessions. `ParallelOverlappingImplementationsPreserveBothChangesThroughConflictRetry` selects an eligible shared thread through the blocker/history contract (or intentionally skips it with no native blockers), then exercises separate Git worktrees and branches. Together these cover the session and Git contracts without a live model or external service; they do not establish what a model inferred from prior conversation.

Session sharing does not choose a branch or base. `ExecutionRunner.Request` uses its execution repository, `CodexExecutor` explicitly sets the active child directory even on resume, and `GitRepository` creates and verifies worktree ownership independently. The repository gate serializes shared Git mutation; unrelated implementation and validation remain concurrent. The thread gate additionally serializes turns that advance the same inherited conversation.

The historical investigation in [session-sharing-parallel-integration-investigation.md](session-sharing-parallel-integration-investigation.md) predates this first-attempt regression fix. Its conclusion that no defect was reproduced applies to that earlier investigation, not to the confirmed verification mismatch above. No claim is made here about the incident's exact patch overlap or live model behavior. Inspecting the preserved incident workspace, reconciling uncertain Git/push state, and resolving incomplete or unverifiable conflicts remain separate recovery work requiring human review.
