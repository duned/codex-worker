# Guided Worker enrollment and association

From **Workers → Add Worker**, select **New machine** or **Existing Worker**. The destination is the configured HTTPS administration origin. Use a certificate trusted by the Worker OS with the correct hostname; neither the dashboard nor the CLI offers a TLS bypass. The Worker initiates outbound HTTPS. No inbound Worker ports, SSH or remote shell are required.

The new-machine instruction uses the Server assembly's release version to pin the Ubuntu 24.04 x86_64 installer and Worker archive. The installer also fetches the starter configuration and service unit from that tag, and verifies the archive checksum. The matching published release must include `--pair`; development builds cannot make an older published release support it. For source-build acceptance, use locally built matching Server/Worker binaries on disposable machines. This task does not publish a release or change product versions.

Run the instruction in a local interactive terminal. The installer asks for any missing Worker Git name/email, creates protected service-account state and runs enrollment as that account. Copy the **complete public pairing request** printed by the Worker into Add Worker. It contains the identity, operation and destination, not a credential; operators need not inspect identity files or use a Server authorization CLI. Confirm the displayed destination and selected operation. Choose **Authorize this operation**, reveal the temporary authorization if necessary, and paste it into the node's hidden prompt. It expires after 15 minutes, is single-use and bound to this Worker and operation in the destination registry. Do not paste the Server management token. No token files need to be created or removed.

The authorization is held only in the current dialog, cleared on close, navigation, sign-out, expiry or progress checks, and never placed in commands, URLs or browser storage. API responses use `no-store`. Existing registration transport retains certificate and hostname verification and never follows authenticated redirects. The node alone persists its private pending material and durable API credential with existing protected-file semantics.

Choose **Check progress / Resume** after local acknowledgement and service startup. A registry row without a current authenticated heartbeat is waiting for communication. Registration plus observed communication leads to **Prepare this Worker**, not execution-ready status. Guided enrollments and associations start with scheduling disabled; tool/account setup, project eligibility and explicit scheduling administration remain separate.

## Existing Worker and recovery

Association reads the existing identity and fails if it is missing or invalid. Use the installed configuration and service account. Before changing Server, drain the old association, finish or reconcile active leases, and stop the local service. Add Worker cannot stop an unknown node or grant local administrative permission. Destination association is refused while that identity has active destination assignments, including at authorization consumption. The association preserves configuration, execution history, cached snapshots and uncertain worktrees/recovery resources. It does not transfer active leases or revoke credentials at the previous Server. Retained snapshots never grant scheduling authority at either Server. Follow existing reconciliation paths for uncertain resources before further execution.

A refresh/reload does not preserve the temporary authorization. Paste the same public request again and check progress. On the node, rerun the same instruction and submit **empty input** at the hidden prompt to reconcile retained pending or already published credentials without consuming another authorization. A committed registration with a lost response is verified through the existing acknowledgement and credential protocol. A different pending identity, operation or destination is refused. Preserve its files and resume the original operation.

If retained credentials are rejected and the pending state is not already verified, explicitly request another authorization for the same public request. Expired, used, wrong-identity, wrong-operation or wrong-destination tokens do not authorize replacement. Previously verified pending credentials that are now rejected require operator reconciliation. Missing existing identity requires restoration from protected node storage. Denied permissions require the node administrator. Certificate, hostname or redirect failures require correcting the final endpoint/trust; do not blindly retry, delete pending state or replace identity.

The existing protected `register --token-stdin`, installer token-file/environment paths, standalone mode, and local rotate/recover/associate administration remain supported. Full provider provisioning, comprehensive credential rotation/recovery/migration wizards and the old-registry terminal-history-report 404 defect are deferred. This adapter does not change those execution-report or provider-authentication paths.

## Disposable two-machine HTTPS acceptance checklist

Live checks below were **not run** during implementation. Use two disposable Ubuntu 24.04 x86_64 machines, one Server and one Worker; do not modify operator VMs or use real provider credentials. Record release/build identity, result and diagnostics (redacted) for each check.

1. On the Server machine, configure an HTTPS reverse proxy with a test CA trusted on the Worker, correct DNS hostname, configured `AdministrationOrigin`, and a protected management token. Allow only outbound Worker access to the Server; leave Worker inbound ports closed. Use a release containing pairing or deploy matching local build artifacts.
2. Sign in and open Add Worker → New machine. Verify the exact destination and pinned version. Run the displayed instruction on the clean Worker. Supply Git identity if asked. Paste the public request into the dashboard, issue the one-use authorization, and paste it into the masked local prompt. Check that process arguments, shell history, logs and browser storage contain no authorization or persistent Worker credential.
3. Before starting the Worker, check progress: registration recorded, communication pending, no readiness claim. Start it with no provider credentials. Observe authenticated communication and the preparation link; verify scheduling stays disabled and project execution is unavailable until normal preparation completes.
4. Close/reload during authorization display and during registration. Retain the same public request. Drop the bootstrap HTTP response after Server commit. Retry with empty local input: verify the same pending credential is acknowledged, no second bootstrap is consumed and identity is unchanged. Reload the dashboard and check progress.
5. Repeat with an expired authorization; try reuse and an authorization from a second disposable Server registry on the Server machine. Try mismatched identity and operation. Verify refusal, retained local state, and explicit fresh-authorization/reconciliation guidance. Test wrong hostname, untrusted certificate and an HTTP redirect to another host; no authenticated request may reach that host.
6. For Existing Worker, retain an identity, configuration/history and a disposable uncertain recovery resource. Drain the source Server, reconcile leases and stop the service. Select Existing Worker and run the association instruction against another disposable Server instance on the Server machine. Confirm destination/operation locally, acknowledge, start and check communication. Compare retained files; the source association is not revoked and no active lease is transferred. Try a missing identity and denied local file permissions: neither may create a replacement identity or bootstrap.
7. Keep an active destination assignment while requesting association; verify refusal. Issue authorization while drained, then create an active assignment before consumption; verify consumption is refused without replacing the credential. Finish/reconcile and explicitly retry.
8. Cancel during protected input and outbound registration, then resume the same operation. Verify no late input triggers enrollment after cancellation, and useful pending state survives. Sign out or close the dialog while an authorization response is delayed; it must not be published afterward.
