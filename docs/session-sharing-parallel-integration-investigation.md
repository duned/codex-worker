# Session sharing and parallel integration investigation

> Historical investigation. The later VM2 first-attempt verification mismatch and its fix are documented in [Parallel integration and recovery verification](parallel-integration-recovery-verification.md). The no-defect conclusion below describes the evidence available during this earlier review.

## Finding

The repository evidence does not establish that inherited Codex sessions can select the wrong workspace, branch, or integration base. Session inheritance is optional conversation context. Each Issue still creates its own execution worktree and feature branch, and Git integration remains serialized by a repository-scoped gate. The thread gate serializes only turns that advance the same Codex conversation. A shared thread can therefore reduce parallel implementation for dependent Issues, but it does not serialize unrelated sessions or merge their workspaces.

The reported same-conflict retry is consistent with a real overlapping source change: when the preserved implementation and the advanced base both edit the same lines, retrying that implementation against the unchanged base conflict is expected. The available checkout cannot determine whether the incident had overlapping edits. No defect in the session-sharing or recovery paths was reproduced from local evidence.

## Execution and isolation trace

- **Selection and eligibility:** `BlockerCodexSession.SelectAsync` requires Codex, a native parent, native blocker relationships, matching parent/repository context, and successful blocker history owned by this Worker. Retries explicitly do not inherit a blocker thread. Selection is best-effort context and does not grant execution or managed lease authority.
- **Turn serialization:** `WorkerHost` supplies one `CodexThreadCoordinator` to its workers. The coordinator locks by parsed thread UUID, revalidates eligibility while holding the gate, and marks a thread unusable before running a turn. It is reusable only after success and completion capture; otherwise the next waiter starts a fresh session. A fresh session does not hold the inherited thread gate.
- **Prompt and workspace:** `ExecutionRunner.Request` uses the active `IGitRepository.ExecutionDirectory`. `CodexExecutor` resumes only an explicit recorded UUID and adds `--cd <active execution directory>`, overriding the persisted source session CWD. The prompt describes the current Issue and retry state; session continuation supplies prior conversation, not a path or branch selector.
- **Worktree and base:** `GitRepository.StartIssueAsync` verifies the checkout, refreshes the configured base, records that current HEAD as `_startingCommit`, and creates a worktree at a path derived from the new execution ID with a feature branch derived from the Issue/attempt. Retry-resume copies the preserved recovery delta into a new worktree based on the current refreshed base. Integration-conflict recovery instead validates and reuses the original registered recovery worktree and recorded recovery commit.
- **Integration and recovery:** `ExecutionRunner` validates the active workspace, then waits on its repository gate before integrating. `GitRepository.CommitAndIntegrateAsync` verifies its starting HEAD, fetches the current base, rebases when needed, validates the rebased source, and reconciles a base that advances during integration within a bounded loop. A rebase conflict is aborted and preserved; post-rebase validation failure is preserved with its rebased commit. `StartIntegrationRecoveryAsync` verifies the registered workspace, branch, repository, and recorded commit before retrying integration. #481's standalone resolver is bounded and runs only after recovery intent and ownership verification.
- **Managed and standalone:** Managed execution performs authority checks before Codex turns and again after waiting for the repository gate, before shared Git mutation. Standalone execution has no Server lease, but uses the same worktree, thread, repository-gate, and persisted recovery boundaries; #481's automatic conflict resolution is restricted to standalone conflicts.

## Deterministic local coverage and reproductions

The test suite already provides local-repository reproductions for the relevant interactions without live Codex:

- `CodexThreadCoordinatorTests.ChildrenSharingAThreadSerializeResumeAndCompletionCapture` coordinates two turns on one UUID and proves the second cannot resume until the first captures completion. `DifferentThreadsAndFreshSessionsRunWhileAnotherTurnIsActive` proves different and fresh turns can proceed concurrently. Cancellation and failed-turn tests verify waiters do not reuse uncertain context.
- `GitWorktreeTests.ConcurrentExecutionsRetryRebasedValidationAndReleaseCapacity` runs concurrent executions against a temporary local remote. One execution advances the base while another is validating; the second is rebased and validation is retried against the new parent. It exercises both passing and exhausted bounded validation retries.
- `GitWorktreeTests.PreservedValidationFailureCanRetryIntegrationWithoutAnotherRebase` verifies a preserved rebased conflict retry uses its recorded workspace/commit and does not repeat the already-completed rebase. `CodexResolvedRebaseConflictContinuesAndValidatesBeforeIntegration` and `FailedValidationAfterRebaseStopsBeforeIntegration` cover conflict resolution and preservation around validation.
- `WorkerV011Tests` covers #481 automatic standalone conflict resolution, rejection/exhaustion, and preservation semantics.

These tests exercise the session gate and Git gate independently and exercise concurrent Git integration with deterministic fake validation/implementation seams. No test currently couples a real inherited Codex thread to two Git worktrees: a real Codex process would be required to prove model behavior, and its process contract is separately covered by argument/session tests. The deterministic seams establish the host's scheduling and Git behavior, but cannot establish what a model inferred from a prior conversation. Disjoint changes integrate after base advancement; truly overlapping edits produce an ordinary Git conflict. The existing local conflict tests establish preservation/retry behavior for that latter case.

No source change was warranted: review found no confirmed isolation or recovery defect to fix. For #493/#494, capture the two patch sets and compare their touched paths/lines and base commits. If they overlap, resolve the preserved conflict against the advanced base (with bounded validation); if their edits are disjoint, investigate the exact Git/recovery state and whether the integration base advanced during recovery. Session inheritance alone is not evidence of a wrong worktree or base.
